# Landing Rules — Universal Knowledge Base

Универсальные правила сборки лендинга, применимые к любому продукту в любой индустрии. Используются на Шаге 6 (сборка) и в pre-flight чек-листе перед деплоем.

---

## 1. Изображения — критические правила

- **❌ НИКОГДА не использовать base64** для картинок в HTML
  - Base64 раздувает HTML, картинку нельзя обновить без правки кода
  - Визуальные редакторы (Framer, Webflow) не работают с base64
  - Если встречается в унаследованном файле — вытащить и заменить на ссылку
- **✅ Только относительные пути** (`./images/hero.webp`) или внешний CDN
  - `raw.githubusercontent.com/USER/REPO/main/filename.webp` — для GitHub
  - Cloudinary / S3 / CloudFront — для внешнего хостинга
- **✅ WebP формат по умолчанию** — размер и визуальное качество проверить на реальном файле; универсального процента экономии нет
  - Конвертация через [squoosh.app](https://squoosh.app) (бесплатно, в браузере)
  - `<picture>` с fallback на JPEG для старых браузеров
- **✅ Имена файлов — осмысленные и стабильные** (`hero.webp`, `product_screenshot.webp`, `testimonial_avatar.webp`)
  - НЕ `image-1.jpg`, `img_20240419_141532.png`, `DSC00123.jpg`
  - Обновление картинки = загрузка нового файла **с тем же именем** → HTML не трогаем
- **✅ Пользователю явно указывать** какие картинки нужны: имя файла, примерный размер, куда положить в репо
- **Иконки:**
  - Inline SVG (лучше всего — для перформанса и стилизации)
  - Или CDN-библиотеки: [Lucide](https://lucide.dev), [Heroicons](https://heroicons.com), [Phosphor](https://phosphoricons.com)
  - НЕ emojis как иконки (не адаптируются под тему, палятся как "sloppy")

## 2. Код и структура файлов

> Раздел написан для трека по умолчанию — статический HTML + Tailwind. Если на Шаге 6 выбран Next.js, Astro, Framer или Webflow, структура файлов берётся из фреймворка, а правила ниже применяются к содержимому: без base64, WebP, осмысленные имена, минимум абстракций.

- **Один `index.html` в корне репозитория** — без фрагментации на компоненты, которые неудобно править словами
- **CSS и JS инлайном внутри HTML**, если объём не критичен
  - Если CSS слишком большой (>20 KB) → выносить в `style.css`, предупреждать юзера
- **Комментарии на русском** (если юзер русскоговорящий) — линейный код с понятными секциями
- **Без лишних абстракций** — юзер будет давать команды LLM, не редактировать руками
- **Legal-документы — отдельные HTML файлы** в корне (`privacy.html`, `terms.html`, `cookies.html`) — состав зависит от региона (определяется в Discovery)

## 3. Адаптивность

- **Mobile-first подход** (не desktop-down)
- **Брейкпоинты:**
  - 375px — мобильный (iPhone baseline)
  - 768px — планшет
  - 1024px+ — десктоп
- **Touch-зоны минимум 44×44px** (iOS HIG требование)
- **Меню на мобильном** — бургер или компактное (не полный nav)
- **Проверять все блоки на всех разрешениях** перед деплоем

---

## 4. Производительность

- **Минимум внешних зависимостей** — каждая внешняя загрузка замедляет LCP
- **Анимации через CSS** (transitions, keyframes). JS только если CSS недостаточно
- **Lazy loading для изображений ниже first screen:** `loading="lazy"`
- **SEO + Open Graph метатеги обязательно** (title, description, og:image 1200×630)

## 5. Формы

### Default pattern (для юзеров без backend)

```
HTML form → Google Apps Script (doPost) → Google Sheets
```

Этот путь подходит для учебного или малотрафикового проекта без чувствительных данных. Для заметного трафика, платежей, здоровья, данных детей, документов и другой чувствительной информации нужен специализированный backend с rate limiting, журналированием и CAPTCHA/Turnstile.

### Правила работы с Apps Script

- **Endpoint не меняется** при обновлениях формы (ломается связка с таблицей)
- **Старые поля остаются под теми же именами**, новые добавляются сверху
- **При изменении набора полей — напомнить юзеру обновить шаблон** в `doPost`, иначе новые поля не попадут в Sheets
- **Минимальная защита:** honeypot, allowlist имён полей, ограничения длины, защита от повторной отправки и мониторинг спама
- **Минимизация данных:** собирать только то, что влияет на следующий шаг; рядом с формой объяснить цель и дать ссылку на Privacy Policy

### Валидация

- **Браузерная** — `type="email"`, `type="url"`, `required`, `pattern`
- **❌ Без кастомных JS-проверок** формата (overkill для лендингов)
- **По email-доменам ничего не отсекать** — принимать все адреса

### Инструкция для юзера (при подключении формы)

1. Создать Google-таблицу
2. Расширения → Apps Script
3. Вставить готовый скрипт (предоставляется в продукте)
4. Развертывание → Новое развертывание → Веб-приложение
5. Доступ → Все
6. Скопировать URL развертывания и вставить в форму

## 6. Аналитика и пиксели

- **GTM контейнер переиспользуется** при миграциях доменов — не создаём новый
- **Facebook Pixel / Google Ads pixel — через GTM** с триггером Window Loaded
  - ❌ НЕ инлайн в HTML (блокирует рендер)
- **Cookie consent и pre-consent blocking** настраиваются по конкретному региону и типу технологии. Для EU/UK несущественные cookies обычно блокируются до согласия; CCPA/CPRA требует отдельной проверки disclosure, opt-out sale/share и Global Privacy Control, а не механического копирования GDPR-баннера.
- **Schema.org JSON-LD** — только типы и свойства, которые соответствуют видимому содержимому страницы. Не добавлять FAQ, Review, AggregateRating, HowTo или BreadcrumbList без реального блока на странице.

---

## 7. Стиль и тон

- **❌ НИКАКИХ эмодзи** — ни в ответах LLM, ни в контенте лендинга
  - Эмодзи = сигнал low-effort, AI-generated, непрофессионально
  - Для икон — inline SVG или Lucide/Heroicons/Phosphor
- **❌ Избегать "тильдовского" дизайна** — перегруженные градиенты, блёстки, overlapping shapes, corporate blue-purple AI-стартапов 2022–2023
- **✅ Копирайт в футере — всегда актуальным годом** (автоматизировать: `<span id="year"></span>` + `document.getElementById('year').textContent = new Date().getFullYear()`)
- **Стиль определяется в Step 5** через выбор юзером одного из 1, 3 или 5 hero-вариантов (из 88 стилей UI/UX Pro Max) — **нет "дефолтного" направления**

## 8. Структура лендинга — гибкая в зависимости от задачи

**Принцип:** структура подбирается под JTBD + цель лендинга + landing pattern из 34 patterns UI/UX Pro Max. Нет фиксированного шаблона "8 секций всегда".

### Обязательные элементы (всегда)

- **Hero** с H1 на primary barrier, CTA с глаголом действия
- **Footer** — минимум: ссылки на legal (состав зависит от региона), контакты, копирайт с актуальным годом

### Опциональные элементы — включать по необходимости

| Секция | Когда включать | Когда НЕ включать |
|---|---|---|
| Проблема / Боль | Сложный продукт, нужно объяснить что болит | Простой продукт с self-evident value |
| Решение / Features | Есть конкретные преимущества, которые не в hero | Простой продукт, где ценность видна из hero |
| Social proof | Есть реальные отзывы / логотипы / цифры | Pre-launch (заменить на "waitlist count") |
| Pricing | Прямой checkout / транспарентная модель | Enterprise (Request Demo) / beta |
| FAQ | Есть 4+ частых возражения из reviews | Короткий лендинг с одним focused CTA |
| Финальный CTA | Длинный лендинг, нужно повторить в конце | Короткий single-screen landing |
| Comparison table | Конкурентная ниша, нужно показать differential | Unique product без прямых конкурентов |
| Video/Demo | Сложный продукт, нужно показать в action | Простой SaaS с описательным hero |

### Длина лендинга зависит от задачи

- **Fakedoor / проверка гипотезы** — полноценный лендинг той же длины, что и для продукта; отличается только social proof (`[FILL: waitlist]` вместо отзывов)
- **Product landing** — 4–6 секций
- **Long-form sales page** (premium, $499+) — 8–12 секций
- **Docs/resource page** — зависит от информационной плотности

### Правила выбора структуры

1. Прочитать JTBD и primary barrier из Step 3
2. Выбрать landing pattern из 34 patterns (UI/UX Pro Max) по keywords из brief
3. Адаптировать pattern: убрать нерелевантные секции, добавить нужные
4. **CTA можно повторить** 2–3 раза в длинном лендинге, но не в коротком (выглядит продающе)

## 9. Pre-flight checklist перед деплоем

- [ ] Нет base64 в HTML
- [ ] Все изображения в WebP с fallback
- [ ] Имена файлов картинок осмысленные
- [ ] CSS inline или отдельный файл (не оба)
- [ ] Эмодзи отсутствуют
- [ ] Копирайт футера — текущий год
- [ ] Mobile breakpoints проверены (375 / 768 / 1024)
- [ ] Touch targets ≥ 44×44px
- [ ] Lazy loading на below-fold images
- [ ] SEO meta (title 55–60, description 150–160)
- [ ] Open Graph meta (og:image 1200×630; PNG/JPEG для широкой совместимости)
- [ ] Schema.org JSON-LD присутствует
- [ ] Legal-документы ссылаются из footer (состав — по региону из Discovery)
- [ ] Cookie consent (если применимо к региону)
- [ ] Form endpoint не изменён (если обновляется существующая форма)
- [ ] H1 существует и отвечает на primary barrier
- [ ] Hero проходит "5-second test"
- [ ] PageSpeed Insights прогнан (mobile + desktop)

## 10. Красные флаги — что НЕ делать

- ❌ AI-slop фразы: "revolutionary", "game-changing", "unleash", "seamlessly", "transformative", "empower", "cutting-edge", "next-generation"
- ❌ "In today's fast-paced world..." и аналогичные intro
- ❌ Perfect round numbers ("10x", "100x") без контекста и cite source
- ❌ 3-column blocks everywhere по умолчанию (diversity of layouts)
- ❌ AI-generated stock photography (всегда палятся — avatars, team photos, happy workers)
- ❌ Монотонный ритм предложений (все одной длины → короткие + длинные вперемешку)
- ❌ Gradients 2023-era AI startups (purple-to-blue, pink-to-orange)
- ❌ Floating UI-cards в стиле SaaS homepages 2022
- ❌ Sparkles / stars / magic-wand icons (если не brand-intentional)
- ❌ "Generate your [thing] in seconds!" на CTA (overused)
- ❌ "Trusted by 1000+ companies" без конкретных логотипов/имён
- ❌ FAQ-вопросы "Is it safe?", "Will I like it?" (очевидно-generic)
- ❌ Stack icons row (AWS + Docker + React + ...) — выдаёт SaaS-slop
